# zzz Clickable Terminal Notifications Design

## Goal

When a macOS completion notification from `zzz` is clicked, return keyboard
focus to the exact terminal session that launched the background command. Show
that terminal application's icon for both success and failure notifications.

The first implementation supports iTerm2 and Terminal.app. Its target adapter
boundary must allow future terminal integrations without changing detached
command execution.

## Existing Behavior

`zzz` delegates to `cli_core::command_log`, which launches the user's
interactive shell in a detached process group and returns control to the prompt
immediately. The detached shell redirects command stdout to
`~/.commands/{yymmdd}/{hhmmss}-{command_name}.log`, captures the final status,
and invokes `/usr/bin/osascript` to display a success or failure notification.

The existing notification is posted by `osascript`. It does not retain the
launching terminal session, its icon is not the terminal's icon, and clicking it
cannot reveal the original window, tab, or split.

## Herdr Findings

Herdr exposes two relevant delivery paths on macOS:

- terminal delivery emits native notification control sequences such as OSC 9;
- system delivery prefers `terminal-notifier -activate <bundle-id>` and falls
  back to `osascript`.

OSC 9 lets iTerm2 attach its current window, tab, and split indices to a native
notification. That path is elegant, but iTerm2 gates terminal-generated alerts
behind a per-profile setting. Runtime verification on the target machine
confirmed that the configured profile consumes OSC 9 without presenting a
notification.

`zzz` therefore follows Herdr's system-delivery path for predictable delivery,
then improves it: instead of activating only the terminal bundle,
`terminal-notifier -execute` invokes a validated internal `zzz` focus handler
with the exact launch-time locator.

## Supported Terminal Contract

### iTerm2

At `zzz` invocation time, capture the UUID portion of `ITERM_SESSION_ID`. The
UUID remains stable if tab or window indices change while the command runs and
is inherited when `zzz` runs inside Herdr.

After completion, post through `terminal-notifier` with:

- title `zzz`;
- subtitle `Succeeded` or `Failed`;
- the sanitized command basename as the message;
- `-appIcon` pointing to the installed iTerm2 icon; and
- `-execute` containing the internal focus command with the iTerm2 UUID.

When clicked, constant AppleScript checks that iTerm2 is already running,
activates it, locates the matching session, and selects its containing window,
tab, and split session in that order. If the session has closed, iTerm2 is
activated without creating replacement UI. If iTerm2 has quit, the handler
returns without relaunching it.

### Terminal.app

At invocation time, capture the controlling `/dev/tty*` path. The completion
notification uses Terminal.app's icon and an internal click command containing
that TTY.

When clicked, constant AppleScript checks that Terminal.app is running,
activates it, locates the tab whose `tty` property matches, selects that tab,
and raises its window. If the tab has closed, Terminal.app is activated without
creating a new tab or window. If the app has quit, the handler returns without
relaunching it.

macOS may request Automation permission the first time the click handler
controls iTerm2 or Terminal.app. If permission is denied, focus remains
unchanged and no additional dialog is generated by `zzz`.

### Fallback

Resolve `terminal-notifier` from `PATH` and the standard Homebrew locations
`/opt/homebrew/bin/terminal-notifier` and
`/usr/local/bin/terminal-notifier`.

If it is unavailable, retain the existing `osascript` notification. This
fallback still reports completion but cannot guarantee the terminal icon or
exact-session click behavior. Full interaction requires `terminal-notifier`.

### Future Ghostty Support

Represent the click target as a fixed terminal kind plus an opaque,
terminal-specific locator. A future Ghostty adapter can add its own stable
surface locator and focus implementation without changing notification or
command execution.

Ghostty 1.2 exact-session automation remains outside this change.

## Architecture

Add a macOS-only notification module behind `cli_core::command_log`. It owns:

1. launch-time terminal detection and target capture;
2. notifier and icon resolution;
3. success and failure command construction;
4. terminal-kind and locator validation; and
5. constant AppleScript focus adapters.

The detached wrapper receives fully constructed success and failure commands.
It never re-reads terminal environment variables after the user may have moved
elsewhere.

The `zzz` binary exposes one undocumented, reserved internal focus mode. It
accepts only `iterm2 <uuid>` or `terminal </dev/tty*>`, rejects missing or extra
arguments, and never interprets malformed locators as commands.

## Data Flow

1. `zzz` validates its command-line arguments.
2. It captures the terminal kind, stable locator, current executable, notifier,
   and terminal icon.
3. The detached interactive-shell command starts and `zzz` returns.
4. The wrapper runs the command and captures its exit status.
5. The wrapper posts a success or failure notification.
6. Notification execution is isolated in a subshell so even notifier exit
   failures cannot replace the command status.
7. Clicking the notification launches the internal focus mode.
8. The adapter selects the original terminal target and activates its app.

## Security and Quoting

Command arguments remain excluded from notification text because they may
contain credentials. Only the already-sanitized executable basename is shown.

iTerm2 locators must be canonical UUIDs. Terminal.app locators must begin with
`/dev/tty`, contain no path separator after that prefix, and use a small ASCII
allowlist.

Every executable path, icon path, terminal kind, and locator embedded in a
shell command uses the existing single-quote escaping primitive. AppleScript
values are positional `osascript` arguments, never interpolated into source.

Notification delivery is best effort. Its stdout and stderr do not enter the
command log, and its failure never replaces the user's command status.

## Error Handling

- Exit status zero reports `Succeeded`; any non-zero status reports `Failed`.
- Failure to detect a supported terminal uses the generic notification.
- A missing `terminal-notifier` uses the generic notification.
- A missing icon omits `-appIcon` while preserving click behavior.
- A closed target activates the already-running app without creating UI.
- A quit target app is not relaunched.
- Denied Automation permission leaves focus unchanged.
- Non-macOS behavior remains unchanged.

## Testing

### Unit and Integration Tests

- Parse iTerm2 session values and retain only valid UUIDs.
- Detect Terminal.app and validate captured TTY values.
- Reject unknown terminal kinds and malformed locators.
- Resolve notifier paths in deterministic priority order.
- Resolve iTerm2 and Terminal.app icon candidates independently.
- Build success and failure notifier commands with the exact target.
- Prove click-command values are shell-quoted.
- Prove AppleScript uses positional locator arguments.
- Prove malformed internal focus invocations fail synchronously.
- Prove notification failure preserves command status.
- Preserve existing detached logging, alias, and version behavior.

### Runtime Verification

1. Deliver successful and failing notifications and confirm both entries through
   `terminal-notifier -list`.
2. Select a different iTerm2 session, move to another app, execute the same
   internal command used by `-execute`, and prove the frontmost app and current
   session UUID return to the original Herdr/iTerm2 session.
3. Repeat with Terminal.app when the host grants Automation permission.
4. Confirm installed terminal icons are passed through `-appIcon`.
5. Confirm log output and original command statuses remain unchanged.

## Documentation

Update both README languages to describe:

- clickable iTerm2 and Terminal.app notifications;
- exact launch-session restoration, including iTerm2 sessions hosting Herdr;
- `terminal-notifier` as the dependency for full behavior;
- macOS Automation permission;
- generic fallback behavior; and
- no replacement window when the original target has closed.

Keep the standalone `zzz` install command unchanged.

## Scope

This change does not add Ghostty 1.2 automation, create terminal windows,
surface command arguments in notifications, change `dev-tools silent`, or
alter non-macOS command execution.
